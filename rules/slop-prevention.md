# Slop Prevention: verify before you claim

> A result counts as done when it has been checked, not when it looks done. Always loaded. Long form with the three triggers and the review patterns: `~/.claude/docs/reference/slop-prevention.md`.

- **Give the work a check you can run** (a test, a build, a linter, a diff against a fixture, a screenshot next to the mockup) and run it before you report. Quote the command and its result; "tests pass" without the output is not evidence.
- **Report the verdict first.** The first line of a completion report is `Done: yes` or `Done: no — missing: <list>`. Where the result has several surfaces the user can see, mark each as `verified` or `not checked`. Something unfinished is never reported as finished.
- **Visible results need rendered proof.** A user interface, a game graphic, a layout or any other output the user will look at is fixed only when you have run or rendered it and looked at it: take the screenshot, describe in words what is actually there (elements, colours, positions, values), then judge. A check of the declaration or data that feeds the render does not count. A test that only reads what the fix itself wrote can only agree with itself. If no way to render exists yet, build one before you claim done.
- **Compare against the source**: the file on disk, the screenshot the user sent, the running program. Your own summary, a plan's restatement or a helper's report of it is not the source.
- **Verify where the effect lands.** A fix that keeps data from reaching an external service is proven by what that service really receives (captured call parameters, a dry run that prints the real target list), through the same code path production uses. A second, separately written counter can pass while the real path is still broken.
- **Collect the results of checks your action triggered** (security review, lint pass, asynchronous verification) before you claim done.
- **Do not build on unverified code.** Before you extend code that was generated recently (see `git log`) or that still has type or lint errors, verify it: read it, run its tests, and bring the error count down first. An edit that adds features while the error count stays flat or rises builds on an unverified base. For a larger scaffold, have a fresh `code-reviewer-agent` review it before you extend it.
- **After a wave that claims to match a spec, a source or a design, run a counter-check**: a separate agent whose job is to list every place where the result does not match. Ask it for deviations, not for confirmation.
- When the task was to make tests pass, diff afterwards for deleted tests, weakened assertions and commented-out cases.
